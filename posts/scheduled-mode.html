定时任务为什么一直“错过”：消息模式继承与幂等锁的两个坑 ​

背景 ​

某 Agent 平台把“回答模式”从逐条可选改成按会话首次接纳固定：会话的第一条消息被服务端接纳后，模式即冻结，之后不可切换。我审查的是实现该规则的一个合并请求，重点不在主流程，而在“其他调用方是否遵守新契约”。

模式的权威来源是首个接纳回执。规则本身没问题，问题出在一个写入口没有读它。

现象 ​

现象一：先创建一个尚未首次执行的定时任务，在首次执行前打开它的空会话，用普通输入框手动发一条图文消息；此后定时触发每期都失败，任务被记为“错过／冲突”，不产生新的执行轮，也不会自愈。

现象二：某条图文请求的 HTTP 确认丢失，本地进入“结果未知”。用户删除本地跟踪项后模式锁被正确保留；但随后一条无关请求被拒绝（禁止类，无自动恢复动作），删除这条失败项时，更早那条未知请求的模式锁被一并清除。界面解锁，用户可选出与实际模式不符的后续请求。

影响面：前者让图文模式下创建的任务在特定操作后事实性永久失效；后者让客户端违反“已接纳或结果未知时不解锁”的约定，持续发出必被拒绝的请求。两个缺陷都定级 P2。

排查：从假设到证据 ​

假设一：调度提交缺模式字段，新校验把“省略”当成默认模式。 我先静态审查两条路径的字段传递，再用生产服务类加窄存储替身跑“创建任务 → 手动首条图文 → 触发”。触发返回模式锁定错误，调度器把不可重试冲突记为“错过／冲突”，没有新的执行轮。成立。

假设二：该前置状态只能靠改库构造，理论上不可达。 我用真实组件渲染任务卡与输入框，经模拟桥提交一条图文消息：入口存在，请求确实带图文模式，1 项探针通过。假设被证据否定，路径从界面可以正常走到。

假设三：现象二是偶发界面抖动。 串联真实客户端应用与命令队列，构造“确认丢失 → 删除未知项 → 另一请求被禁止类拒绝 → 删除失败项”，对正确行为（仍应锁定）断言。断言失败：实际解锁，且后续请求不再带模式字段，全程只读快照 1 次、未触发对账刷新。锁是按会话整体删的。

假设四：后续增量改动已顺带修好。 第二天我拉取最新提交、新建独立副本重跑，并补真库周期对照。两条路径仍复现；增量改的是对账与展示，没碰继承与锁归属。

根因 ​

缺陷 A：继承点缺了一次读。 权威来源是首个接纳回执，但调度触发构造内部命令时省略了模式字段。公开命令“省略即默认”被不加区分套用到内部调用方，内部触发被当成默认模式，与冻结的图文模式冲突；调度器把不可重试冲突按“错过”结算且不建执行轮，于是每期必冲突、永不自愈。权威值只有一个来源，但有一个写入口没读它。

缺陷 B：锁没有身份。 失败结算按会话维度无条件删除“未对账模式锁”，锁不携带建立它的命令身份。一次拒绝只能证明“当前命令未被接纳”，不能证明更早那条结果未知的命令未被接纳。这是幂等状态机里典型的证据越界。

修复方案与取舍 ​

A：调度侧显式继承。 调度提交时读取会话已冻结模式并继承，把该模式写入后续每一轮的执行回执；公开命令“省略即默认”保持不变。优点是单一权威来源、回执自洽；代价是调度侧要能读到会话状态，需明确读失败时的降级策略。

B：跳过冲突校验，照默认模式写入。 能跑，但会产生错误模式的回执，把污染推给下游。否决。

C：锁与命令来源绑定。 拒绝时只释放当前命令能确证的那一条，更早的未知锁按命令来源保留，等权威回执到达后再按身份对账。代价是锁从“一会话一值”变成“一会话多来源”，要补过期与身份切换时的清理规则。

D：收到拒绝就刷新快照再判定。 实测不触发刷新（快照只读 1 次、无需对账标志为假），且刷新也不能证明更早请求未被接纳。

我的建议是 A + C，原则是“不绕过校验、不把一次拒绝当作另一条命令的对账证据”。验收标准：标准与图文模式各连续两轮触发均被接纳、回执模式一致；没有手工首条消息的任务保持默认；拒绝后模式入口仍锁定，权威回执到达后能正常对账与清理。

为什么全绿还能有缺陷。 95 项覆盖的是单条路径：会话内提交被正确冻结、命令被拒后提示正确、序列化字段完整。没有一条从“创建任务”走到“手动首条图文”再走到“周期触发”，也没有一条把两条不同来源的命令放进同一个会话的锁状态。流水线跑的就是这些用例，绿是绿在覆盖面之内——测试通过只证明已覆盖部分正确。另外 209 项按名称筛选的库测试只筛选、未执行，不计入通过或跳过。

复盘 ​

一、新契约要按调用方清单过一遍。 “省略即默认”是对外命令的语义，不是所有调用入口的语义；内部调用方应显式传值。改契约时我会列出全部写入口，比通读主流程有用——主流程通常是对的，漏的总是旁路。

二、幂等状态要有身份。 锁不记来源，就只能按会话整体删；一删就把别人的证据一起删掉。锁至少带命令实例、会话、建立时间与来源，释放要可确证：同一命令被明确拒绝，或权威回执证明其未被接纳。另一条命令的失败是独立事件，不构成解锁证据。还要补过期或租约、身份切换与登出时的整体清理、多来源锁的合并读取。

三、绿灯要问覆盖了哪条路径。 95 项全绿、4 个 Job 全成功，与两条路径仍复现并不矛盾。判断缺陷是否存在，看路径有没有被走到，不是看套件颜色。真库复现要设对照组，状态要通过生产入口造，不要直接写 SQL 造行，否则复现不出真实分支；断言要写正确行为，而不是现在错成什么样。

局限。 我这一轮没有做修复后验证，也没拿到实现方对两条根因的确认；P2 是定级，不等于已被接受。真库复现的首轮执行轮由终态夹具置位，没有调用真实模型，不能表述为真实部署或模型链路验收。探针“通过”有两种含义：断言错误状态的通过是复现成功，只有断言正确行为的通过才代表合理。未跑原生桌面壳、打包产物、预发环境与全量本地流水线；没有“修复后行为”的数据，是最大的空白。
