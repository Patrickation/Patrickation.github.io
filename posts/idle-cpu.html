常驻 Agent 服务的空闲 CPU 治理：从 16% 到 1.7%，以及三次未达标的迭代 ​

背景 ​

某金融终端 Agent 平台是"桌面客户端 → 云端协调 API → Agent 执行运行时 → PostgreSQL"的链路，助手实例和数据库同机部署，数据库跑在 Linux 容器里。服务是常驻的，没有任务也一直活着。

现象 ​

只开着客户端、什么都不做，数据库容器就占 1.47 个核。

30 秒窗口、8 逻辑处理器：桌面端加后端的 Windows 进程 CPU 合计 16.08%（按 8 逻辑处理器归一，不含容器虚拟机），同一窗口数据库容器原始 CPU 147.24%（100% 约一个逻辑核），事务 373.74 次/秒，新建连接 0.89 次/秒。没有报错，功能也正常，是典型的"默认一直空转"。同事在 Mac 宿主 + Linux 容器上复现，产物已含上一版修复，可以排除"没更新代码"。

桌面客户端 ──HTTP──> 云端协调 API ──任务/事实──> 执行运行时 ──SQL──> 同机容器 PostgreSQL

排查：从假设到证据 ​

先怀疑容器。数据库在容器里，CPU 又记在容器账上，很像配额或参数问题。停掉应用、只留数据库，容器 CPU 中位数 0.86%。这个方向被否定：容器只是负载出现的位置，不是原因。

假设一：空队列也在开事务。 读队列工作器源码，25ms 定时器，空结果分支同样开事务、跑完整领取查询。写源码探针：真实定时器跑真实空分支，数据库换成只返回空行的替身。3.002 秒内任务领取 776 次、事实投递 1552 次（默认 4 消费者），合计 2328 次 SQL API 调用，775.4 次/秒，每轮都含 BEGIN/COMMIT。真实 30 秒窗口里，四类领取分别 977、109、460、460 次 calls。

这里我修正过自己：775 次/秒是 API 调用数，含事务控制，不是 QPS，也不是 CPU。它只能证明"空队列在开事务"这个行为，定量必须上真实实例。这个分工后来成了纪律。

假设二：就绪自检成功也销毁连接。 四个角色每轮合计 92 次 SQL API 调用，成功时销毁 4 条连接；空闲窗口新建连接 0.89 次/秒。检查成功也在付建连与认证成本。失败、超时、取消时丢弃是必要的，成功提交后应当归还连接池。

假设三：修完后端就到底了。 可逆对照否定了它：同一修复后后端、同一窗口，只暂停或恢复桌面空闲动画，Windows 进程 CPU 从 10.54% 降到 1.11%。Electron 渲染进程 10 秒采样：LayoutCount 1445→136，RecalcStyleCount 1445→181，TaskDuration 2.164→0.283 秒；空页面有 6 条持续 SVG 动画。桌面端是独立热点，量级和后端相当。

假设四：复用连接会不会带脏事务。 只在完整事务提交成功且未 abort 时归还，其余一律销毁。只读回归 2 文件 35 项通过；新建连接 0.89→0.10 次/秒（-88.9%）。

假设五：剩下的是执行还是规划。 用真实运行时角色做 EXPLAIN 与规划统计：30 秒累计规划 5026.3ms、执行 650.7ms，差一个量级。给两条队列加保守候选预检（先一次廉价存在性判断，没有候选就跳过原事务），预检语句固定命名以复用计划。四类复杂空领取 calls 归零，规划 711.6/724.6ms，执行 614.5/579.6ms，容器 CPU 34.74%→9.20%/9.21%，事务仍约 75 次/秒。事务频率没降，恰好说明领取语义没被削减。

假设六：结构指纹。 表结构/约束指纹每 5 秒重算一次。先做只读评估：系统目录查询改成物化子查询或命名语句，没有稳定收益、指纹一致，放弃。再做有界"结构证明"复用：单一检查者、绑定迁移契约与全部账本字段、只在完整事务提交成功后发布、失败/超时/abort/显式刷新/关闭即失效、迟到成功不回填。每类指纹从每 5 秒一次降到 60 秒 3 次（约 -75%）；默认预留与探针预算让实际约 20 秒重验一次。

根因 ​

不是单点 bug，是四个"空闲也照做"的默认行为叠加：①空队列开事务，且每次重新规划；②就绪自检成功也销毁连接；③桌面空闲动画持续触发布局；④结构指纹每 5 秒重算。前两项是数据库侧主成本，后两项解释了"只修后端"为何仍有残高。

修复方案与取舍 ​

方案 A（否决）：整体调慢轮询、减少投递消费者、给容器加 CPU 上限。前两个不消除空事务，还牺牲吞吐与取消时延；配额只压最高消耗，让延迟变差。

方案 B（采用）：分层治理。空闲有界退避 25→50→100→200→250ms，本机提交后即时唤醒；两条队列加保守候选预检；预检与发现语句固定命名；成功提交后归还连接；只保留有限眨眼动画；结构指纹改为最长 30 秒的证明复用。

代价要写明：控制队列完全空闲可退避到 250ms，跨实例取消最多多约 225ms 轮询等待（另加数据库耗时与基础 tick）；结构证明最长 30 秒有效，管理员手改列或约束的发现会延迟，但普通业务角色没有 DDL 权限。没有采用全量 LISTEN/NOTIFY：写入方覆盖、未来到期、重连补扫与连接预算都没设计好，只当提示又保留 25ms 兜底，控制主项降不下来。

验证结果 ​

口径：W 是 Windows 宿主指定进程 CPU 时间按 8 逻辑处理器归一，不含 Docker VM；C 是容器原始 CPU，100% 约一个核；T 是事务计数差除以时长；N 是新建连接每秒；P 是累计规划耗时。W 与 C 分母不同，不能相加，也都不是整机总 CPU。

这些数字不代表什么：本机是 Windows 宿主 Node ＋ 同机 Linux 容器 PostgreSQL、8 逻辑处理器，不代表 Mac/ARM，也不代表 macOS 客户端或完整 Linux 应用镜像的部署形态。窗口都是 30 或 120 秒，在回归与构建结束后采集，机器不独占；只证明本机该场景的前后对照，不代表长期容量、活跃积压吞吐或稳定性。第 1 轮、复测与第 2–5 轮是不同时间点的独立对照，数字不可跨组混用。T 含事务边界，不是复杂查询 QPS；P 含等待因素，不能按 CPU 占比分摊。

复盘 ​

  1. 先量再改，把"行为证据"和"成本证据"分开。探针只能告诉我谁在开事务，真实实例才能告诉我贵不贵。此后我一直四组一起看：容器 CPU、事务、新建连接、规划耗时。
  2. 可逆对照比解释有力。只切一个变量（动画、诊断配置），并把偏高的窗口一起留下，比挑最好看的数字更接近真相。
  3. 优化前先列不变量。默认 4 路投递、控制队列独立、5 秒安全检查、锁/租约/取消/ACK/schema 都不动；不变量守住，数字才有解释力。

没做到的部分：目标是空闲容器 CPU 均值 2–5%，五轮下来第 3–5 轮没有稳定达到。第 3 轮 9.87%→7.55% 是同窗口 -23.53%，仍在目标之上；第 4 轮默认配置只差约 2%；第 5 轮两窗口 9.63%/6.28%、平均约 7.96%，与 8.20% 基线差约 3%，波动大于收益，所以不宣称达标。可压缩的重复规划在前两轮基本吃完（34.74%→9.20%），剩下的是固定控制轮询、就绪自检与跨实例周期发现；继续要走"跨副本通知 + 持久兜底"，那是设计变更，不是调参。Mac/ARM、完整 Linux 镜像、真实供应商、活跃积压与多实例长期稳定性都还没验收；一次渲染层用例超时也没定位，我没有改断言或超时。
