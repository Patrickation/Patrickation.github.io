跨请求的会话一致性：为什么“操作结束时检查”不够 ​

背景 ​

某金融终端 Agent 平台的账户读取工具只读自选股与持仓，复用桌面端登录态：设备 Cookie 留在桌面端，云端只存加密的最小来源材料，运行时按当前执行身份取回结果。

关键在调用形态：一次工具调用不是一次 HTTP，而是一次操作内串行发起多笔上游读取——默认自选、分组、交易账户发现、逐账户持仓。期间会话可能因重新登录被替换，运行也可能被取消。所以“凭据现在还能不能用”不是进门时判断一次，而是每笔外部 I/O 的前置条件。

现象 ​

我看到的实现却是：整次读取进入前复核一次执行与会话，结束后做一次结果接纳。当新登录会话在另一服务实例提交，或取消事务已提交，读取器仍用第一笔请求时捕获的旧 Cookie 把后续 GET 发出去；持仓循环会继续向剩余账户发请求。每笔请求自身只查进程内取消信号，看不到数据库里已提交的会话 revision 与执行状态。

越界发生在“请求是否发出”，不是结果层。最终栅栏有效——换代返回安全的会话变更错误，取消则拒绝结果；审查没找到跨租户返回、凭据进入模型上下文或取消结果被错误接纳的证据。定级 P2，不升级为数据泄漏。

排查：从假设到证据 ​

先怀疑读取器，被证据否定。 我的第一反应是读取层写错：某处缓存了 Cookie，或漏了取消检查。从编排入口向下读调用链，发现每个请求方法都查了本地取消信号，代码没写错；它能查到的只有本进程状态，这才是问题。对照合同文档“每次外部 I/O 前复核”的条款，整条链上复核只有一处，只包在整次读取前后。

第二个假设：窗口太窄，到不了。 写了两组探针：窄替身组 2 项，在第一笔响应的处理窗口内等另一实例完成登录替换；真实 PostgreSQL 容器组 2 项，等真实取消事务提交。两组都断言“第二笔 GET 仍带旧 Cookie、最终结果被拒绝”，都通过——此处通过是复现成功，不是行为正确。窗口不需要多窄，只需要存在：另一实例提交是异步的，进程内信号不会因此自动取消。

实例 A（读取器）           数据库              实例 B
    |                       |                    |
    |-- 复核：执行+会话 v1 ->|                    |
    |<-- 通过 -------------|                    |
    |                       |<-- 登录替换 -------|
    |                       |   会话 revision→v2 |
    |-- GET #1（Cookie v1）|                    |
    |   （处理响应，窗口）   |                    |
    |   ✗ 没有第二次复核    |                    |
    |-- GET #2（Cookie v1）| ← v2 已提交后仍出网
    |-- 栅栏：v1≠v2 → 拒绝结果                 |

第三个假设：是否已扩大到数据越权。 逐项审最终栅栏、字段允许名单、结果编码与活动记录，找“跨租户返回／凭据外泄／取消结果被接纳”的反例，没找到。这个否定结论把定级钉在 P2，也说明要修的是“别再发出去”，不是“别把结果交出去”。

根因 ​

这是典型的检查粒度错配：复核的粒度与副作用的次数不匹配。授权与会话状态是每笔外部 I/O 的前置条件，实现把它当成整次操作的准入检查。后果三条：一次操作内复用同一份捕获凭据，状态变化与后续请求之间留下窗口；唯一的进程内取消信号观测不到另一实例已提交的换代或取消；最终栅栏只保证“结果不被接纳”，不保证“请求不被发出”。两者混为一谈，“结果正确”就掩盖了“过程越界”。

一句话：第 1 笔请求前的复核通过，不等于第 2 笔请求前状态没变。最后一次检查通过，不等于中间没有越界。

修复方案与取舍 ​

我建议落地“逐请求复核”：读取器新增必填的复核回调；编排层在每笔上游 GET 前，用短事务比对当前执行授权、用户与原会话 revision，一致才发请求；复核事务先提交、连接先释放，再进网络等待；前后各查一次取消信号；保留最终结果栅栏，覆盖“最后一笔在途时状态才变化”的窗口；旧凭据返回 401 时不做误判，也不误伤并发产生的新会话。

否决三个方向：只依赖进程内信号或本地广播——看不到跨实例已提交的变化；只在结束时统一复核——拦得住结果，拦不住已出网的请求；整次操作包进长事务——网络等待期间持锁占连接，与“等网络前释放连接”的约定冲突。代价是每笔 GET 多一次短事务往返，延迟影响本次未测；前置复核负责“不发”，结果栅栏负责“不接纳”，是分层而非替代，窗口不能降为零。

红测试怎么写。 我的写法是不 mock 掉编排层：用真实编排层、真实读取器加合成上游响应，把“另一实例提交变化”放进第一笔响应的处理窗口并 await 提交完成，再捕获第二笔请求实际携带的凭据。断言写“第二笔仍带旧凭据、最终结果被拒绝”，它在旧实现上通过代表复现成功，评审时不能读成行为正确。修复后同一用例改成“第二笔请求没有发出”，保留“最后一笔在途结果仍被拒绝”。最关键的是请求次数：这个场景应只有 1 次 GET，旧实现实际发了 2 次——这是把缺陷钉死的那条断言。同一场景还要在真实数据库容器里再跑一遍以覆盖跨实例，并保留“无变化时正常读取”的对照组。

口径与边界。 计数以项目自带测试命令的分文件结果为准；红绿对照是同一用例在旧实现与新实现上各跑一次。数据库为随机端口一次性容器，跑完清理，全程未连业务库；上游是合成 HTTP 响应。“修复后”一列只代表自动化环境里第二次 GET 没有发出，不代表真实账户链路验收；自动化通过只说明“接线与合同在自动验证环境内闭合”，不等于真实账户可用；探针修复前“通过”是复现错误、修复后“通过”是拦截成功，不能混读。

复盘 ​

一、检查的位置决定它能否阻止副作用。 同一个“复核”，放在操作两端，语义是“准入 + 接纳”；放在每笔 I/O 前，语义才是“副作用的前置条件”。我现在的做法是先问要阻止的是结果还是请求，再决定放哪。

二、进程内信号不是跨实例状态。 取消信号、广播、内存事件都只代表本进程看到的世界。状态可能由另一实例提交时，必须在副作用前读一次权威存储；读的时候用短事务，先提交、释放连接，再进网络等待。

三、红测试的“通过”要标语义。 复现缺陷的用例断言的是错误行为，它在旧实现上通过，读报告的人容易当成“行为正确”。应单独命名并在报告里分开标注；修复后换成断言正确行为，两次“通过”含义不同，不能放进同一张绿灯表。

没做到的部分。 真实账户联调没做，真实网关、桌面登录链路与发布验收不在本轮；真实自选与交易接口字段、Cookie 域与交易登录标识绑定、持仓成功路径都未验收。每笔 GET 多一次数据库往返的延迟影响没测。修复只保证“已提交的变化之后不再产生新请求”，不能把最后一笔在途请求的窗口降为零。维护者的 Review 结论、是否合并，以及那 2 项符号链接用例的复验，也都还留着。
