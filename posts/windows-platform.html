Windows 上那些“看起来像权限问题”的错误：进程边界、路径编码与入口后缀 ​

背景 ​

某 Agent 平台的本地开发环境跑在 Windows 上。本地数据库和桌面端入口要先过一道私密文件权限预检，预检内部会拉起 PowerShell 读 ACL；前端预览包构建则走另一条链。两轮排查下来，三处报错分别指向“权限不足”“文件找不到”“必须用包管理器启动”，看起来都像配置或权限问题，实际分属三个层面：进程创建、路径表示、外部契约。

现象 ​

  1. 本地数据库启动脚本和桌面端入口都在预检处退出。日志只留下一行内部错误码和退出码 1。同一目录用 Get-Acl 手工看是正常的，三条允许规则看起来也对。自动化侧拉不起来，只能请用户在自己的终端执行。
  2. 前端预览包构建时报入口无法解析。日志打印的路径形如 /D:/...%20...：前面多一个斜杠，空格变成 %20。
  3. 包管理器升级后，启动准备的 CLI 标识校验不认新入口：旧入口是 .cjs/.js，新版是 .mjs。这条是读代码判定的，原始报错没有留下。

排查：从假设到证据 ​

一、先怀疑 ACL，六步取证把它排除 ​

我先怀疑目录 ACL 不合规：继承项混入、owner 不对、缺少允许主体。写了一个参数化取证脚本，按六步读：路径是否存在且为目录、是否 reparse point、当前用户 SID、目录 ACL 类型、owner SID 是否在允许集合、逐条规则打 OK/VIOLATION。

结果六步全 ok，rule_count=3。三条都是非继承的 Allow FullControl，主体分别是当前用户、SYSTEM、Administrators；owner 就是当前 SID；原始导出还证明父目录的继承项没有落到这个目录。ACL 合规，预检说的“权限不足”不是权限模型的事实。

那问题只能在“读 ACL 的通道”上。先让 PowerShell 落一个标记文件，能写出来；再用 33 行最小脚本在 Node 里直接拉起 powershell.exe，带 -NoProfile -NonInteractive，15 秒超时。结果是 SPAWN_FAIL / STATUS=null / CODE=EBUSY，消息为 spawnSync ...powershell.exe EBUSY；该会话里 PowerShell 的 stdout 也不回显。

结论：不是没有权限读 ACL，而是当前进程树不允许再创建 PowerShell 子进程。预检拿不到输出，就把“通道失败”翻译成了“权限失败”。

二、预加载补丁：能跑，但等于伪造校验 ​

最省事的做法是用预加载补丁把校验 stub 掉，让启动先过去。评估后否决：预检的意义就是证明私密文件权限，绕过等于让启动在“未证明权限”的状态下继续。既然 ACL 已经合规，补丁唯一的作用是把环境限制藏起来。

最后保留 ACL 和校验不动，把启动动作移到不受限的终端。同一天 15:01，同一个最小复现返回 SPAWN_OK，项目自带的数据库脚本打印本地就绪回执；容器此前已 healthy，复用未重建。这说明差异在执行环境／进程树，不是代码回归。但策略按会话还是按进程树生效，我没有取证确认。

三、构建失败：.pathname 不是文件系统路径 ​

先怀疑路径拼接错了：相对/绝对混用、分隔符写错。用 pathToFileURL 对同一文件复算，分别取 .pathname 和 fileURLToPath：前者得到 /D:/...%20.../构建配置，前导斜杠、盘符没去、空格被百分号编码；后者是正常的盘符路径。

再怀疑构建器对入口格式敏感。看报错确实落在入口和输出两处解析，把这两处改成 fileURLToPath(new URL(...)) 后重跑，构建通过：121 个包，单次 191 秒。构建器无责。URL.pathname 返回的是 URL 路径段，不是文件系统路径；POSIX 下两者恰好同形，所以这段代码在 Linux/macOS 上“看起来能用”，只在 Windows 暴露。修复范围就是同一份构建配置里的两处。

四、入口后缀：把文件名当成了版本契约 ​

先怀疑包管理器调用方式失效（shell 引号、路径拆分）。读代码发现已经是 shell:false，并用 process.execPath 显式执行 CLI，避免 cmd.exe 拆分含空格路径——这是此前为 Windows 修过的，方向正确。

真正的问题是入口扩展名校验：旧白名单只认 .cjs/.js，新版入口是 .mjs，校验直接抛“必须经包管理器启动以提供 CLI 标识”。原意是“必须经包管理器启动”，实现却把入口文件名当成了版本契约。修复只是把正则补上 mjs，其余语义不动。

启动 / 构建失败
├─ 预检报“权限不足”
│  ├─ 六步读 ACL ── 全 ok ──→ 不是权限模型
│  ├─ 直接 spawn PowerShell ── EBUSY ──→ 进程创建被拒
│  └─ 换执行位置 ── SPAWN_OK ──→ 环境边界，不是代码回归
├─ 构建报“入口无法解析”
│  ├─ 看报错路径 ── /D:/...%20... ──→ 是 URL 路径段
│  └─ 改 fileURLToPath ──→ 121 个包构建通过
└─ 预检不认 CLI
   ├─ 看调用方式 ── 已是 shell:false ──→ 调用无责
   └─ 看入口名 ── .mjs 不在白名单 ──→ 契约没跟上版本

把三次放在一起看，区分环境与缺陷的顺序是：先看错误码属于谁——产品语义码还是 OS 错误码；再做最小复现矩阵，一次只减一个变量；最后问“不改代码，这个错误还能不能被解释”。ACL 六步取证加 spawn 复现，两条证据合起来才排除了权限问题；构建与入口后缀则是代码可解释、修复后即通过，且不依赖宿主策略，才判为产品缺陷。

根因 ​

  • 进程边界：受限进程树里无法创建 PowerShell 子进程，spawnSync 返回 EBUSY、status=null。产品预检依赖“spawn 再解析输出”这条通道，通道一断就表现为权限校验失败。
  • 路径表示：new URL(import.meta.url).pathname 在 Windows 上返回带前导 /、盘符未去、空格百分号编码的 URL 路径段，被当成文件系统路径传给构建器。
  • 外部契约：包管理器升级改变了 CLI 入口扩展名，预检白名单没跟上；失败信息只说“要用包管理器启动”，指向性不足。

查到了什么： ACL 六步全 ok、3 条非继承 Allow、owner 正确、非 reparse；直接拉起 PowerShell 得到 EBUSY/status=null；换执行位置后 SPAWN_OK；两处 .pathname 改为 fileURLToPath 后 121 个包构建通过；白名单补 mjs 后启动准备 success=true。

没查到什么： 15:01 恢复的具体成因没有取证，是按会话还是按进程树生效不清楚；没有在 CI、其他 Windows 版本、WSL 或容器里复验；没有跑 test／typecheck；191 秒、71.054 秒只是单次记录，不是稳定基线。

修复方案与取舍 ​

  • 改 ACL 或放宽预检：否决。ACL 本来合规，改它只是迎合错误假设；放宽则让“私密文件不得被其他主体读取”的保证失效。
  • 预加载补丁 stub 校验：否决。等于伪造安全校验结果，让真实缺陷无法暴露。
  • 保留校验与 ACL，改执行位置：选择。代价是短期内自动化侧不能自动启动，需要人工一步。
  • 手工 replace(/^\//, '') + decodeURIComponent：否决。只覆盖本次两种症状，遇到 +、#、UNC 或非 ASCII 还会错。改用 fileURLToPath，由标准库处理盘符、编码与平台差异。
  • 继续 shell:true 加手工引号：否决。cmd.exe 的参数解析不可控。保留 shell:false 加 process.execPath 调 CLI，白名单补 mjs；代价是多一步 CLI 存在性判断。

复盘 ​

三条可迁移经验：

  1. 错误码的归属要和 OS 的事实对齐。产品抛的是业务语义码，OS 抛的是 EBUSY/EPERM/EACCES。先问一句：不改代码，这个错误还能不能被解释？能解释就是环境，解释不了才是缺陷。
  2. 最小复现要一次减一个变量，证据要落盘。换终端、换父进程、换机器、直接调 OS 原语；本例 PowerShell 的 stdout 被吞了，只能靠写文件取证。不要用“补丁能跑”当验证。
  3. 跨平台代码在 POSIX 上能跑，不代表正确。URL 路径段和文件系统路径是两套表示；外部契约（CLI 入口名、路径格式）要有契约测试，不能只测 happy path。

局限： 没查清进程策略为什么在 15:01 消失，也没能把这条差异搬进 CI。宿主策略、终端防护、沙箱这类不可复现的限制，只能靠 capability probe 记录并显式 skip，不允许静默通过；这部分我做到了记录，没做到自动化。
